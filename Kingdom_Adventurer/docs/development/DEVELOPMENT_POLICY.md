# 開発基本方針

## 目的
最終仕様は維持し、最小ゲームから機能単位の追加・詳細化を繰り返す。常に遊べる状態を維持する。

## 初期ゲーム
Kingdom Observer の世界表現と「森のサバイバル」の操作感を参考に、実際の既存コード・ゲームを確認してから設計する。流用の可否や開発エンジンは未確定。
- フィールド、固定配置の街、プレイヤー移動、カメラ追従、HP、敵の簡易出現・行動、基本戦闘、宿、最低限のUI・死亡再開処理。
- 街の機能施設は宿のみ。接触時に休むか YES/NO で確認し、YES で無料全回復、NO で回復せず戻る。
- 経験値、レベル、装備、アイテム、ダンジョン、魔法、経済、NPC生活AI、国家運営等は初期対象外。敵の報酬なし。敵出現は簡易処理。
- 数値・死亡再開方式・具体的操作・素材は暫定設定とし、最終仕様を変更しない。

## 開発サイクル
1. 最新コミット、ROADMAP、TODO、DEVELOPMENT_STATUS、OPEN_QUESTIONS、現行仕様書、仕様・実装対応表、変更履歴を確認。
2. 次の機能を依存関係、遊びやすさ、手戻り、現在の不足から選ぶ。新機能を優先しつつ必要な詳細化も行う。
3. 関連する統合仕様書と出典の history 原資料を着手前に必ず全文確認。矛盾は独断で確定しない。
4. 対象と完了条件を TODO に登録し、実装・動作確認・既存機能の回帰確認を行う。
5. 下記の資料更新・完了条件を満たし、遊べる状態を維持してGitHubにコミットする。実行可能な限り次の項目へ進む。

## ゲームの表示バージョン

- ゲームを修正するたびに、`game/index.html` の画面見出し（`h1`）の末尾にある `ver.N` を、作業開始時の最新版から1つ上げる。機能追加、不具合修正、数値やUIの調整も含む。
- 同じ修正の実装と資料更新でコミットが分かれる場合も、繰り上げは修正ごとに1回とする。変更履歴に新しい番号を記録し、公開ページの見出しがその番号になったことを確認する。
- CSSを変更した場合は、表示バージョンの更新に加え、[ゲームREADME](../../game/README.md#css更新時)の手順でCSSのURLも更新する。

## 拡張性
機能別コード、世界データと描画の分離、固有ID、設定値の分離、依存関係、保存形式の拡張性、画面外の世界処理を考慮する。ただし不要な機能や空の仕組みを先行実装しない。必要な再設計・置換を許容し、既存機能を壊さない。

## 仕様・進捗管理
[統合仕様](../specifications/README.md) と [原資料](../history/README.md) を根拠とする。暫定・簡易実装と正式実装を区別し、簡易機能の完了を最終仕様の完了とみなさない。残る詳細は TODO に追加する。未決事項は OPEN_QUESTIONS に記録し、必要な場合のみユーザーに確認する。完了・未完了の正本は TODO、現在の引き継ぎは DEVELOPMENT_STATUS、Phase は ROADMAP とする。定期的に全仕様と TODO・実装を照合する。

## 現行仕様・実装・変更履歴の必須管理

- [現行仕様書](../specifications/current/CURRENT_SPECIFICATIONS.md) は現在のコードの挙動の正本となる説明資料。目標仕様とは区別し、実装済みの条件・数値・例外・暫定挙動を記録する。実行時の数値はコードを正本とし、資料と一致させる。
- [仕様・実装対応表](../architecture/IMPLEMENTATION_MAP.md) は現行仕様IDとファイル・関数・設定・関連仕様の多対多対応を管理する。逆引きも同期する。
- [変更履歴](CHANGELOG.md) は変更前後・理由・関連ID・影響範囲・検証結果・完全な実装コミットSHAを累積記録する。過去記録を上書きしない。
- 現行仕様ID（CUR-分野-連番）は永続とし、目標仕様IDと区別する。新規仕様に新IDを付け、変更・ファイル移動で既存IDを変更しない。廃止・分割・統合時は旧IDと後継関係を履歴に残し、再利用しない。

### 変更時の必須手順
1. 新機能・突然の修正依頼・不具合修正・数値調整・内部改善を問わず、着手前に現行仕様書と対応表から対象ID・実装箇所・関連仕様を特定し、実コードと呼出元・依存先を確認する。変更履歴から過去の理由を確認し、必要に応じGit差分を読む。対応表だけを根拠に影響範囲を断定しない。
2. TODOに対象・関連ID・完了条件を登録する。関連する目標仕様と原資料の確認義務は従来通り。目標仕様の変更が必要なら独断で確定しない。
3. 実装し、対象機能と影響する既存機能を検証する。未実施の検証と理由を明記する。
4. 実際の変更後コードを読み、現行仕様書を更新する。新規仕様は追加、変更は該当IDの本文更新。挙動不変なら変更不要と判断できる。対応表のファイル・関数・関連仕様・逆引きも確認し、追加・移動・削除等を反映する。
5. 実装をコミットし、確定した完全SHAをCHANGELOGに追記する。TODO・DEVELOPMENT_STATUSも更新し、資料更新をコミットする。現行仕様書・対応表の更新は実装コミットに含めてもよい。履歴自身のSHAを自己参照させない。
6. 最終確認として、変更後のコード・現行仕様・対応表・変更履歴・TODO・進捗が整合することを確認する。更新不要の資料は理由を記録する。未完了・未検証を完了と扱わない。

**コード実装だけでは開発完了としない。必要な資料更新、検証、コミット、引き継ぎまで完了条件とする。** 中断時は未完了作業と再開地点をDEVELOPMENT_STATUSに残す。資料のみの重要変更もCHANGELOGに記録するが、履歴追記だけのコミットは再帰的に記録しない。
